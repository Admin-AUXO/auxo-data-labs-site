**In short:** A pilot rarely costs much. A pilot that runs on every ticket, lead and invoice, every day, can. Four controls keep it in check: routing, effort, caching and batching. Measure cost and quality per task before you scale.

## Why does the bill creep up?

Say a small pilot works well, so the team points it at every ticket, lead and invoice. Months later, the finance lead opens the usage report and the total is higher than the plan. Nothing is broken. It just runs far more often than anyone planned for.

Four controls help. Use them in this order, then measure.

## Route each task to the right model

The current Claude models differ widely in cost. Haiku 5.5 costs a small fraction of Opus 5.5, and Fable 5.2 costs more than either. Sending every task to the biggest model is the most common way to overspend.

Routing means each task goes to the smallest model that does it well. Simple sorting goes to Haiku. Everyday drafting goes to Sonnet. Hard analysis goes to Opus or Fable.

Anthropic describes two patterns for combining models. In one, a lower-cost model does the work and passes hard decisions to a stronger one. In the other, a stronger model plans and hands bulk work to lower-cost ones. Either way, most of the work is billed at the lower rate.

## Set effort deliberately

[Effort](https://platform.claude.com/docs/en/build-with-claude/effort) sets how much the model thinks on each request. More thinking means more tokens, and more cost. Defaults vary by model, so a request you never configured still has a setting.

Run your real tasks at a few effort levels. Keep the lowest one that holds quality. The [effort post](/blog/effort-levels-when-to-think-harder/) in this series shows how.

## Cache what repeats

Many workloads send the same large block of text with every request: a policy manual, a product catalogue, a long set of instructions. [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) stores that block so later requests read it at a much lower price. On the current models, a cached read costs a small fraction of the normal input price.

Caching works best when the shared part comes first and stays the same. It does nothing for content that changes every time.

## Batch what can wait

Not every task needs an answer in seconds. Overnight tagging of the day's tickets, a weekly review of contracts, or a monthly clean-up of CRM notes can all wait a few hours.

Anthropic's [Batch API](https://platform.claude.com/docs/en/build-with-claude/batch-processing) processes requests in bulk at half the normal price. If a task can wait, batching is one of the simplest savings available.

## Measure before you scale

<Callout>
Measure cost and quality per task before you scale.
</Callout>

None of these controls help if you don't know what you are spending, or whether the output is good. Before scaling any AI workflow, have three numbers:

- **Cost per task.** Not per month. Per ticket, per lead, per report.
- **Quality per task.** The share of outputs a person accepts without changes, from a fixed set of real examples.
- **Time saved per task.** Measured against how long the work took before.

Then set a ceiling: a cost per task and a cost per month, with an alert when either is crossed. Agents in particular can loop and spend more than expected. A person approves the ceiling, and reviews it when volume changes.

## What it looks like by function

**Finance.** Batch the overnight coding of transactions on Haiku. Keep the board-pack commentary on Opus, where quality matters most.

**Sales.** Route lead sorting to Haiku in real time. Batch weekly account summaries overnight.

**Support.** Tag tickets on Haiku as they arrive. Cache your help-centre articles so every reply that checks them reads them cheaply.

**Engineering.** Cache the coding standards and repo guide that every review request repeats. Batch the overnight triage of new issues.

## Try this

Pick your highest-volume AI task, or the one you plan to scale next. For one week, record:

1. How many times it ran.
2. Which model and effort level it used.
3. How many outputs a person accepted as they were.

Then ask three questions. Could a smaller model do it? Could it wait for a batch? Does every request repeat the same long instructions? A yes to any of them is a saving to test.
