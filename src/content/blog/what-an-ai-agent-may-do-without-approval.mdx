**In short:** an AI agent may read and draft without approval. Anything that changes your systems needs a review. Anything that sends, posts, pays or hires needs a named person to approve it every time.

Someone on your team wants to try an AI agent. It can read your inbox, update your CRM and draft replies. Nobody has said what it may do without asking.

That gap is where most agent risk sits. Close it before you build.

## Three tiers of action

Sort every action an agent can take by what it touches. Two published guides make the same point. Anthropic's guide to [building effective agents](https://www.anthropic.com/research/building-effective-agents) says agents can pause for human feedback at checkpoints. OpenAI's [practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) names high-risk actions, meaning sensitive, irreversible or high-stakes ones, as a trigger for human intervention. Its examples include cancelling orders, authorising large refunds and making payments.

Here is a plain way to apply that.

**Tier 1: read and draft.** The agent reads documents, summarises, sorts, checks and flags. It writes drafts that nobody has seen yet. No approval is needed. Spot-check a sample so you know the work is sound.

**Tier 2: change something inside your own systems.** The agent updates a record, moves a ticket, changes a status, files a document. These changes stay inside your walls, and most can be undone. Either a person approves them, or the agent writes each change to a review log that a named person reads on a set day. Pick one and write it down.

**Tier 3: act on the outside world.** Send, post, pay, sign, hire. A named person approves every one, every time. No exceptions for "routine" cases. A sent email cannot be unsent, and a payment is hard to recall.

AUXO's own rule is short. An agent drafts, sorts, checks and flags. It never sends, posts, pays or makes a hiring decision without a named person approving. For more on choosing that person, read [name the approver before you build the agent](/blog/name-the-approver-before-you-build-the-agent/).

## Five questions before any agent goes live

This is the risk check. It takes an hour with the people who own the process. If you cannot answer one, the agent is not ready.

1. **What can it read?** List every mailbox, folder, database and file store. Personal data and client confidentiality problems start here.
2. **What can it change?** List every record, field and setting it can write to. Mark which changes are reversible.
3. **What can it send outside?** Email, messages, posts, payments, API calls to other firms. Each is a Tier 3 action.
4. **Who approves?** One name or role for each Tier 3 action, plus a cover for holidays. If nobody responds, nothing goes out.
5. **How do you see what it did?** If you cannot replay a run, you cannot fix a mistake or explain it to a customer.

The [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) is voluntary guidance for managing AI risk to people, organisations and society. It is a useful frame if your board or insurer asks how you assess risk. These five questions are a practical start inside it, not a replacement for it.

## Access and logs

Give the agent the least access that does the job. Start with read-only and add write access one permission at a time.

Run it under its own account, never a person's login. Then its actions are labelled in every system it touches, and you can remove its access without locking out a colleague.

Decide who can switch it off, and make sure they can do it in minutes. That means a named person, a known place to do it and no vendor ticket in the way.

Keep a log of every run: what it was asked, what it read, which tools it used, what it produced and who approved it. Our post on [agents in practice, tools and approvals](/blog/agents-in-practice-tools-and-approvals/) covers what a good trace holds.

## What to test before launch

Test in a sandbox with copies of real data, not live systems. Anthropic recommends extensive testing in sandboxed environments along with appropriate guardrails, because errors can compound over many steps.

Run these checks.

- **Normal cases.** Does it do the job on twenty ordinary examples?
- **Messy cases.** Missing fields, odd formats, duplicate records, another language.
- **Hostile text.** An email or document that tells the agent to ignore its rules. It should flag the text, not obey it.
- **Boundary tests.** Ask it to send, pay or delete something. It should stop and ask for approval every time.
- **Approver tests.** Does the approver see the source next to the draft? Can they reject with one click? Does the queue stay small enough to read?
- **Switch-off test.** Turn it off during a run. Confirm nothing half-finished is left behind.

## When the agent gets it wrong

It will, eventually. Plan for it now.

**Stop it.** The named person switches it off first and investigates second.

**Contain it.** Use the log to find every action it took in the affected period. Reverse what can be reversed. Contact anyone who received something wrong.

**Find the cause.** Was it bad input, a missing rule, too much access or an approver who did not look closely? Fix the cause, not only the symptom.

**Change the tier.** If an action keeps going wrong, move it up a tier. A Tier 2 change that needed a review log may now need approval each time.

## Run the check on your own setup

Most firms find the gaps in the first hour. They are usually in questions one and five: nobody listed what the agent can read, and nobody can replay what it did.
